## Commits and pull requests

The commit history on the default branch follows
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/#specification). The
release automation reads those commit messages to decide the next version and to build the
changelog, so the format is load-bearing rather than stylistic.

Pull requests are squash-merged: the whole branch collapses into one commit, and **that
commit's message** is what gets parsed. Depending on the repository's
`squash_merge_commit_title` setting, that message comes either from the pull request title
always (`PR_TITLE`), or from the single commit's own message when the branch has exactly one
commit (`COMMIT_OR_PR_TITLE`, the more common setting across `gravity-ui/*`).

So do not rely on the title alone: **give the last commit the same message as the pull
request title**, and both paths land the same text. Every commit must be a valid Conventional
Commit anyway — a husky `commit-msg` hook runs `npx commitlint -e` — so never bypass it with
`--no-verify`.

Of the types in the specification, only three release anything: `feat` (minor), `fix` and
`perf` (patch). The rest — `docs`, `style`, `refactor`, `test`, `build`, `ci`, `chore`,
`revert` — are valid and merge fine, but ship nothing. Choose the type by what the change
does to users, not by what feels tidy: a user-visible fix filed as `chore` fails silently —
CI is green, the pull request merges, and nothing reaches anyone.

## Releases

Never edit `CHANGELOG.md` or the `version` field in `package.json` by hand. Both are
generated by [`gravity-ui/release-action`](https://github.com/gravity-ui/release-action), and
a manual edit conflicts with the open release pull request.

A merged pull request is not a published version: the release action accumulates changes into
a release pull request, and merging *that* tags the version and publishes to npm.

## Gravity UI dev skills

This repository shares its development conventions with the rest of `gravity-ui/*`. They are
packaged as agent skills in
[gravity-ui/skills-dev](https://github.com/gravity-ui/skills-dev).

- Opening a pull request → invoke the `gravity-ui-pr-create` skill.
- First `gh` command of the session, or any `gh` failure → invoke the `github-cli-setup`
  skill.
- Initializing the portable repository overview eval → invoke the
  `repository-overview-eval-init` skill.

Not installed? In Claude Code: `/plugin marketplace add gravity-ui/skills-dev`. For Codex,
OpenCode and project-wide setup, see
[installation](https://github.com/gravity-ui/skills-dev#quick-start).
